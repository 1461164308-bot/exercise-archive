1. **macOS 未实机验证**：代码路径已实现（`sips` 转 BMP + 纯 Python 解码、tkinter 跨平台、
   PDF 走浏览器打印），但本机为 Windows，未在 mac 上跑过。文档中已标注。
2. **云端链路未接真实厂商 Key**：本机没有可用的云端 Key、也不便用你的账号产生费用。
   已用「本地假 OpenAI 兼容服务 + 真实 HTTP 往返」把 **HTTP 层、Bearer 认证、Base URL 三种写法、
   请求体结构、`response_format` 降级重试、500 错误处理、text-only 模式、cloud_first 端到端识别、
   云端深度分析、本地不可用时的兜底路由** 全部验证通过（`python tools\verify_cloud.py`，详见第三章第 6 节）。
   仍需你自己确认的只有「真实厂商返回内容的质量」：按 `docs/05-模型与云端接口配置教程.md` 填好
   Base URL / 模型名 / Key，点界面上的「测试连接」与「获取模型列表」即可。
3. **单图多题的图像切分未做**：一道大题的多小问会各自入库，但归档共用同一张原图
   （升级方向第一条已给出 bbox 方案）。
4. **PDF 的两条路径**：正常环境优先叫系统 Edge/Chrome 无头打印（文字可选、体积小）；
   本机开发沙箱禁止浏览器创建进程间通道，因此实测走的是**内置渲染器**（GDI 渲染 + 无损嵌入，
   中文不会变方块，代价是文字不可选）。两条路径都有验证。
5. **显卡被占用会导致识别变慢甚至超时**：本机实测过一次——游戏独占 GPU（90%、显存 4.4G）时
   4.4B 模型无法完全装入显存，推理退化到 CPU，单图超过 300 秒超时。自检新增「显卡」一项会
   直接报出占用率与空闲显存；`docs/03-常见问题排查.md` 附录二有完整处置办法。
6. **识别准确率非 100%**：手写潦草、反光、折痕严重的图片仍可能读错；界面上所有字段都可手动
   修改并保存，建议核对后再用于复习。
7. **公式排版是"自研子集"**：支持上下标、分式、根号（含次数）、积分/求和/极限上下限、矩阵/行列式、
   希腊字母与常用关系符；**未实现**的 LaTeX 特性包括 `\left(...\right)` 的自动伸缩括号、
   `\overbrace`/`\underbrace`、多行对齐环境（`align`/`split`）、化学式（`\ce{}`）、
   自定义宏。遇到不认识的命令会**降级为可读文本**（不会报错、不会丢内容）。
   如需扩展，改 `exerarchive/mathdraw.py` 的 `CMD_SYMBOLS` 与 `Renderer.layout` 即可，
   渲染对照图用 `python -m exerarchive.mathdraw verify/math-preview.png` 自查。
8. **公式图是位图而非矢量**：界面与 HTML/Word 里的公式按目标字号渲染成 PNG，
   放大到很大时会略有锯齿（TXT/Markdown 走纯文本写法，PDF 走浏览器打印时为矢量排版）。

**关于那次真实识别一开始为什么慢 —— 这是本次复核最有价值的一条发现**：

第一次跑，单图 47~130 秒、只有 6.6 tok/s，比第五章表格里的 5~8 秒/图慢了十几倍。
逐步查下去，因果链是这样的（每一步都有实测数字）：

| 步骤 | 观察 | 结论 |
| --- | --- | --- |
| ① 看显存 | 7815 / 8192 MB 被占，只剩 0.4 GB 空闲 | 模型装不进显存 |
| ② 查进程 | 5 个 `llama-server.exe`，其中 **4 个比当前 `ollama.exe` 启动还早**（10:03、10:29、17:52、18:19 vs 18:51） | 上一次服务退出时被遗弃的推理子进程，仍占着显存 |
| ③ 清掉这 4 个残留 | 显存 **7815 → 2527 MB**（释放 5.3 GB） | 显存够了 |
| ④ **再跑一次，还是 6.6 tok/s** | `ollama ps` 显示 `size_vram` 只有 **451 MB / 4.2 GB** | Ollama 在**加载那一刻**决定 GPU/CPU 分层，之后**不会因为显存变空而重新规划** —— 模型还停在「10% 上卡」的状态 |
| ⑤ 卸载模型让它重新加载 | `curl … "keep_alive":0` → `ollama ps` 为空 → 再识别 | **74~80 tok/s，6 张共 43.2s，状态 14/14** |

也就是说：**光清理显存不够，必须让模型重新加载一次**，否则速度永远停在慢档上 ——
这正是用户会误判成「软件坏了」的地方。已把这条连同实测数字写进
`docs/03-常见问题排查.md` 附录二（含 `ollama stop` 命令与「怎么确认生效」）。

> 顺带说明：慢速那两次的状态是 13/14，恢复满速后是 **14/14** —— 与第五章如实写过的
> s4 手写体（`getting`）波动一致，快慢两次都出现过，属于模型侧的正常波动，不是回归。
